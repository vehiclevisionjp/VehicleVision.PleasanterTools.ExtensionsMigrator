# ライセンス文書の正本（トリプルライセンス用）

**LGPL-3.0-or-later（A 層）・AGPL-3.0-or-later・商用ライセンス**の 3 層で提供するツール用の正本。
デュアルライセンス（AGPL と商用）用の正本は、リポジトリ直下の `LICENSING.md` などにあり、使い方は [ライセンス](ライセンス.md) の「正本の使い方」にある。
本書は、デュアルとの違いと、トリプルの正本の全文・部品を持つ。現時点でトリプルのツールは **DotNetClient** だけで、そこが実例。

## どちらの正本を使うか

| 提供条件 | 正本 | 例 |
| --- | --- | --- |
| デュアル（AGPL ＋ 商用） | リポジトリ直下の `LICENSING.md` など（Template 自身がデュアル） | Questionnaire ほか |
| トリプル（LGPL ＋ AGPL ＋ 商用） | 本書の全文 | DotNetClient |

A 層（LGPL）の範囲は **利用の目的**で決める（営利事業に使わない個人・非営利団体・教育機関。公的機関は含めない）。
この範囲の文言は法務確認済み（2026-10-29・30）なので、正本の本文から変えない。範囲を変えるときは、先に法務と決める。

## 別の正本一式にした理由

デュアルの正本へ「トリプル用の部品」を足す方式（`license-tier=triple` のような ID）と、別の正本一式を置く方式を比べ、**別の一式**にした。

- **違いが本文の大半に及ぶ。** 層の数と記号がずれる（デュアルは A=AGPL・B=商用、トリプルは A=LGPL・B=AGPL・C=商用）。
  導入文・表・選び方・各層の節・Pleasanter の節の「どの層が壊れるか」・依存の節・CLA の導入文と 1.1 が、すべて記号に依存する。
  部品へ切り出すと、マーカーの外側がほとんど残らず、「外側は全リポジトリで同一」という節マーカー方式の利点が消える
- **デュアルの正本を変えずに済む。** デュアルの `LICENSING.md` などには、空の `tier-a` や `lgpl-note` を足す必要がなくなる。
  デュアルの各リポジトリの監査（`RepoAudit`）の比較対象も、そのまま
- **トリプルはツールが少ない**（現時点で 1 つ）。重複の保守コストが小さい。共通の部品（`usage`・`connection`・`reference`・ノート）は、
  [ライセンス部品](ライセンス部品.md) の本文をそのまま使うので、部品集は 1 つのまま
- 別の一式にすると、デュアルとトリプルの共通部分（Pleasanter の節、依存の節、CLA）の変更を、両方へ入れる必要がある。
  それは、下の「デュアルとの差分」を保守の目印にして防ぐ（デュアルの正本を直したら、この表の「同じ」の行を見直す）

## 置き場

本書の全文は、**コードフェンスの中**に置く（デュアルの部品集と同じ理由。`_documents/` からの相対リンクが検査で壊れるのを避け、機械処理もしやすい）。
適用するときは、フェンスの中身を、リポジトリ直下の同名のファイルへ貼る。製品名は `VehicleVision.PleasanterTools.Template` の文字列で、適用時に置換する。

## 節マーカー（トリプル）

規則はデュアルと同じ（[ライセンス](ライセンス.md) の「節マーカー」）。選ぶ部品は次のとおり。

| | `usage` | `console` / `web-service` / `library` | [ライセンス部品](ライセンス部品.md) と同じ。B（AGPL）の節の末尾に置く |

| | `core` | `none` / `off` | 本書。`on` は、トリプルのツールが Core へ依存するときに、法務と決めて足す |
| `.github/workflows/cla-check.yml` | `cla-intro` | `triple` | [ライセンス部品](ライセンス部品.md)。デュアルの正本は `dual`（既定）で、ほかの部分は同じ |
| `LICENSE-COMMERCIAL.md` | `sni-scope`・`sni-terms` | `off` のみ（`sni` と同じ値） | [ライセンス部品](ライセンス部品.md) の `off` |
| | `core-terms` | `off` のみ（`core` が `none` / `off` のとき） | [ライセンス部品](ライセンス部品.md) の `off` |
| | `reference-scope` | `on` / `off`（`reference` と同じ値） | [ライセンス部品](ライセンス部品.md) と同じ |

`core=none` は「Core へ依存していない」ことを書く節で、`core=off`（何も書かない）と区別する。
依存がないうちは、今後 Core へ依存するときにライセンスの整合を見直す旨を残す（共有の置き場は Core に一本化する方針のため）。

## 適用するとき

1. 事実の確認は、デュアルと同じ（[ライセンス](ライセンス.md) の「事実の断定文は、実態で確認してから使う」）。
   加えて、NuGet パッケージなら `nuget=on` にして、`PackageLicenseFile` が `LICENSING.md` を指し、`LICENSING.md`・`LICENSE-COMMERCIAL.md`・
   `LICENSE`・`COPYING`・`LICENSE-AGPL`・`NOTICE` がパッケージへ同梱されていることを、csproj で確認する
2. `LICENSE`（LGPL）・`COPYING`（GPL）・`LICENSE-AGPL` の全文は、各リポジトリに置く（正本は文言だけを持つ）
3. `cla.yml` と `signed.yml` の注記は、デュアルの正本を使う。`signatories` の記録は残す
4. `README.md` のライセンスの表と、`_documents/ライセンス.md` の層の表も、正本の記号・対象に揃える

```markdown
## どれを選ぶべきか

次の順に確認してください。

1. **個人・非営利団体・教育機関が、営利事業に使わずに利用する** → **A（LGPL）**。追加の契約や費用は不要です
2. **営利事業に使う**（企業・営利団体・個人の営利利用）、または**公的機関**が利用する → **B（AGPL）か C（商用）** を選びます

   （連絡先は [`LICENSE-COMMERCIAL.md`](LICENSE-COMMERCIAL.md) を参照）

### 判断の目安

A かどうかは、**誰が使うか**ではなく、**利用が営利事業に使われるか**で判断します。

- 個人が**仕事・業務（営利事業）で使う**なら、個人事業主・フリーランスを含めて**営利側**です（A ではなく B か C）
- 個人が**趣味・学習など、営利事業に使わない**目的で使うなら A です
- 学校法人・大学などの教育機関が**授業・研究**で使うのは非営利で、A です。営利事業に使うなら A ではありません
- 非営利団体が**営利事業に使わず**に使うなら A です
- **官公庁・自治体・独立行政法人などの公的機関は、A に入れません**（B か C）
- 判断に迷う場合は、上のとおり問い合わせてください。本書は法的な助言ではありません

  静的にまとめて差し替えられなくする場合などは、LGPL の条文を確認してください
- LGPL の条文の解釈は、本書の範囲ではありません。本書は法的な助言ではありません
```

```markdown
## 3 層の違い

| | LGPL v3（A） | AGPL v3（B） | 商用ライセンス（C） |
| --- | --- | --- | --- |
| 対象 | 営利事業に使わない個人・非営利団体・教育機関 | 営利事業に使う場合・公的機関 | AGPL の義務を負わずに利用したい場合（法人に限らない） |

| proprietary 製品への組み込み | 可（LGPL の条件を守る場合） | 不可 | 可 |
| 保守・サポート | なし | なし | 契約による |
```

### CONTRIBUTING.md の CLA 節

見出し「CLA へ署名する」から次の `##` 見出しの手前まで。ほかの節はリポジトリごと。

```markdown
## CLA へ署名する

**貢献は、取り込む前に [CLA.md](CLA.md) への署名が要ります。**
LGPL・AGPL・商用ライセンスのいずれでも提供できるよう、再許諾できる状態を保つためです。

### 手順

1. [CLA.md](CLA.md) を読む
2. 「CLA への署名」の Issue を作り、同意する（Issue テンプレートあり）
3. 管理者が同意と許諾権限を確認し、[.github/cla/signed.yml](.github/cla/signed.yml) へ追記する
4. PR の必須チェック `cla` で確認する

**会社の業務として貢献する場合は、法人用の署名も要ります。** 勤務先の承認を先に取ってください。

### 法人として署名する場合

会社の業務として貢献する場合は、法人用の署名も要ります。**Issue に加えて、署名者の権限を確認できるメール**を、法人のメールアドレスから
`group.development+cla@vehiclevision.jp` へ送ってください。書いていただくことは次のとおりです。

- 法人名
- 署名者の氏名と役職（法人を代表して CLA に署名する権限があること）
- 貢献者として届け出る GitHub のログイン名の一覧
- 署名の Issue の番号
- 法人用の CLA（[CLA.md](CLA.md) の 2）に同意すること

メールの内容は GitHub には載せません（社内で保管します）。確認でき次第、署名の一覧へ追記します。

### 署名済みかどうかの確認

署名一覧は管理者が変更します。貢献者自身の PR で追記しても、その PR の判定には使いません。
一覧の変更を対象 base ブランチへ取り込んだ後、PR を更新してチェックを再実行してください。
未署名ならチェックが失敗し、案内コメントが付きます。

Dependabot・GitHub Actions・`my-repo-automation-bot[bot]` の自動更新 PR は対象外です。
判定の実装は `.github/workflows/cla-check.yml` にあります。
```
