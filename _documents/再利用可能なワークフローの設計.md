# 再利用可能なワークフローの設計

Issue #40 の設計メモ。参照日: **2026-10-22**。
実装・設定変更・共通 workflow の実行試験は行っていない。
全 14 リポジトリの固定 SHA、ファイルの実差、適用中の必須チェックは
[棚卸し](再利用可能なワークフローの棚卸し.md)に分離した。

2026-10-26 追記（Issue #61）: 参照更新 workflow は廃止し、共通化の対象から外す。
本体は AI 用の参照専用で CI は使わず、`scripts/sync-reference.sh` で上流 `main` を必要時に取得する。
日次の追従 Issue / Draft PR や bot の迂回権限は不要で、再現性は文書の SHA・固定リンク・参照日が担う。
各アプリへの [配布手順](参照ソースのオンデマンド取得への配布手順.md) は別紙に示す。
他の workflow の共有方式は本設計のままとし、GitHub の設定や権限はこの変更では変えない。

## 結論

**D（再利用可能なワークフローとコピー配布の自動化の併用）を推奨する。**
必須チェックではない patch 更新系から A へ移し、
`wip-title`・CI・監査・CodeQL など名前が保護設定と結合するものは当面 C に残す。
SHA 更新と呼び出し側スクリプトの配布も C の対象にする。
全ワークフローを一度に A にする案は採用しない。

ただし、**現在の Template は internal、残る 13 リポジトリは public** である。
公開リポジトリから internal の再利用ワークフローは呼べない。
同じ organization でも例外にはならない（公式資料 [S3]）。
Template に置くという目的を満たすには、その公開化について別途承認が必要。
この設計で公開範囲を変更しない。承認までは C を継続する。
公開化しない場合は公開の共通専用リポジトリという代案になるが、置き場所の再合意が必要である。
composite action に替えても、internal → public の共有制約は解消しない。

もう一つの移行条件は **`patch-release.yml` と `release-run.yml` の入力契約の不一致**。
10 リポジトリに同一の patch-release があるが、
`bump`・`dry_run`・`acknowledge` を受ける release-run は 4 リポジトリだけだった。
残る 6 リポジトリを「同じファイルだから動く」として移行しない。
ファイルの存在、静的な互換性、実行成功は別の事実として扱う。

## 1. 現状から分かる共通化の境界

patch-updates と patch-updates-sync は 14 リポジトリでバイト単位に同一。
土台ブランチの判定のような修正を一元化する効果が大きい。
patch-release も設置済みの 10 リポジトリで同一だが、呼び出し先との互換性に差がある。
3 本とも、取得した develop/master ルールセットの必須チェックには含まれない。

一方、PR の Issue 紐付けは「警告だけ」と「PR コメントの作成・更新」に分かれる。
WIP 検査はイベントのタイトルを読む版と API で最新タイトルを読む版がある。
依存レビューはライセンス拒否・コメント投稿・公開範囲による実行条件が異なる。
参照更新は 2026-10-26 に廃止を決定したため、Core への追加も再利用化も行わない。
リリースには採番から PR・タグまで進める版、タグだけ作る版、NuGet 公開、下書き ZIP 公開が混在する。
これらを入力値だけで無理に一つへまとめず、現行の意味を保存する。

## 2. 公式仕様で確認した制約

以下は資料上の確認であり、この設計専用の GitHub Actions 実機試験は **未確認**。
資料の一覧と参照日は末尾に示す。

### 2.1 定義・入力・シークレット

再利用する YAML は `.github/workflows/` 直下に置き、`on: workflow_call` を定義する。
呼び出しは `jobs.<job_id>.uses` で行い、`steps` の action としては呼べない（[S1]・[S2]）。
呼び出しジョブへ `runs-on` や任意の前後 `steps` を加えることもできない。

入力は `boolean`・`number`・`string` のいずれかを宣言し、
呼び出し側の `with` から同じ型で渡す。
`workflow_dispatch` の `choice` は `workflow_call` の型ではない。
シークレットは `on.workflow_call.secrets` に宣言し、呼び出し側から名前を指定して渡せる。
同一 organization / enterprise の呼び出しには `secrets: inherit` も使える（[S1]）。

本案では App 秘密鍵だけを明示的に渡し、`inherit` を既定にしない。
App client ID は呼び出し側の `vars` から string 入力として渡す。
受信側は空値も検査する。`required: true` だけでは秘密の値が空でないことまで保証しない。
秘密の値や生成したトークンをログ・出力・PR 本文へ出さない。

呼び出しジョブでは `environment` を指定できない。
環境シークレットは受信ジョブの `environment` とその優先順位が関わるため、
リポジトリシークレットを渡す設計と混同しない（[S1]）。
workflow レベルの `env` も相互に引き継がれない。
値の受け渡しは入力・`vars`・明示した workflow outputs を使う（[S2]）。

### 2.2 イベントと実行コンテキスト

各リポジトリの `schedule`・`workflow_dispatch`・`pull_request` と、
その `branches`・`types`・`paths` は **呼び出し側に残す**。
Template の cron 一つで全リポジトリが動く仕組みではない。
呼び出された workflow のイベント payload と `github` コンテキストは呼び出し側のものになる
（[S2]・[S5]）。

schedule は既定ブランチ上のファイルを実行する。
14 リポジトリの既定ブランチはすべて develop。
workflow_dispatch の UI 起動も既定ブランチ上の定義が必要となる。
schedule の遅延・公開リポジトリの無活動による停止も残る（[S5]）。
現在の cron は timezone 未指定の UTC として、そのまま維持する。

sync は `pull_request` の `closed`、base が master、
`merged == true`、head が `chore/patch-updates-` という条件を維持する。
再利用化を理由に `pull_request_target` へ切り替えない。

`concurrency` は呼び出し側が所有する。
`github.workflow` は受信側でも呼び出し側の名前になるため、
同じ group を双方へ複写すると、`cancel-in-progress: true` で自分を止め得る（[S2]）。
patch 系の既存の `cancel-in-progress: false` を維持し、多重 PR・多重リリースを防ぐ。

### 2.3 permissions と認証

`GITHUB_TOKEN` の権限は呼び出し側 workflow または呼び出しジョブに明示する。
受信側・ネスト先では同じか狭い権限にしかできず、昇格はできない（[S2]）。
token と repository は呼び出し側のもの。Template を更新するトークンになるわけではない。

| 対象 | 呼び出し側 GITHUB_TOKEN | 別途必要な App 権限 |
| --- | --- | --- |
| patch-updates | `contents: read` | Contents / Pull requests: write |
| patch-updates-sync | `contents: read` | Contents / Pull requests: write |
| patch-release | `contents: read`、`actions: write` | 現行では不要 |

App のインストール範囲は呼び出し元リポジトリだけに限定し、org 全体へ拡大しない。
PR 作成と push は引き続き App トークンを使う。
現行公式資料では GITHUB_TOKEN による一部 PR イベントも承認待ち実行を作るが、
完全自動の連鎖を同等に保証しない。App を使う設計は維持する。
GITHUB_TOKEN による `workflow_dispatch` が新しい実行を起こせることは公式資料 [S6] で確認した。

### 2.4 ジョブ名と必須チェック名

公式のルールセット資料 [S4] は次の形式を明示している。
workflow の表示名や YAML のファイル名ではなく、この **完全な文字列**で照合する。

| 実行形態 | 必須チェックの文脈名 | 改名前後の例 |
| --- | --- | --- |
| 通常のジョブ | `<job name>` | `wip-title` |
| 再利用 workflow のジョブ | `<job name> / <reusable job name>` | `pr-policy / wip-title` |
| matrix を使うジョブ | 展開された実際の名前を採取する | `Analyze (csharp)` など |

呼び出し側の job ID を従来どおり `wip-title` にするだけでは旧名を維持できない。
両方の `name` を同じにしても `wip-title / wip-title` になる。
ネストや matrix を含む最終名は第 0 段階で check-runs API から採取し、
UI だけで推測しない。ルールセットは matrix やイベント種別を区別しない（[S4]）。

影響先はルールセットだけではない。
`scripts/Sync-Ruleset.ps1`、追跡済み ruleset JSON、
release-run の check-runs 照合、運用文書も同時に対応が必要。
現在の必須一覧はリポジトリごとに違い、develop と master でも E2E 要件が違う。
Template の既定 5 個で全リポジトリを上書きしてはいけない。

### 2.5 公開範囲と参照方式

公開の Template を参照する場合も、organization と呼び出し側の Actions 設定が
その public workflow の使用を許可する必要がある（[S2]）。
今回の repository API では 14 件すべて `enabled: true`、`allowed_actions: all`。
ただし公開化後の実呼び出し、上位ポリシーによる実効制限は **未確認**。

`uses: vehiclevisionjp/VehicleVision.PleasanterTools.Template/.github/workflows/<file>@<ref>`
という形式にする。`uses` の ref には入力式を使えない（[S1]）。

| 固定方法 | 利点 | 問題・採否 |
| --- | --- | --- |
| `@master` | 共通修正が次回から一斉に反映される | 同時障害・無審査の動作変更。採用しない |
| 完全な commit SHA | 再現可能、段階移行と個別の戻しが容易 | SHA 更新 PR が必要。本案の既定 |
| `@v1` などの可動タグ | 版系列として伝えやすい | 書換可能で一斉影響。SHA と同じ保証ではない |

公式資料も安定性・安全性について SHA 固定を最も安全としている（[S1]）。
Template の develop で検証した候補を、master に確定した実在の SHA で配る。
SHA の更新 PR は自動生成しても、自動で全件マージしない。
呼び出し ref の更新は残るが、大きな YAML の複製差分ではなく小さな版更新にできる。

ブランチ参照の場合、全ジョブの再実行と失敗ジョブだけの再実行で参照 SHA の扱いが異なる。
後者は最初の試行と同じ SHA を使う（[S2]）。
「再実行すれば常に最新版」ではないことも SHA 固定の採用理由である。

### 2.6 checkout とスクリプトの置き場所

受信 workflow 内の通常の `actions/checkout` は **呼び出し側のリポジトリ**を取得する。
Template の YAML を呼ぶだけでは Template の `scripts/` は手元に現れない（[S7]）。

**第 1 段階は `apply-patch-updates.mjs` を呼び出し側に残す。**
選択した master、無ければ develop を checkout し、その土台にあるスクリプトを実行する。
現在の「土台にスクリプトが無ければ更新を待つ」という条件も保存する。
frontend はスクリプトが Git 追跡済み package.json と lock を探索するため、追加入力は不要。
フロントエンドのパス差があっても、tools/screenshots を含む現在の検出範囲を変えない。
スクリプト・NOTICE 検査・ignore ファイルなどの更新は C で配る。
IndexCreator のスクリプトには実差があるため、同一と仮定して上書きしない。

将来 Template 側から取得するなら、別ディレクトリへ Template の同一 SHA を checkout し、
認証情報を保存せず、submodules も取得しない方式を検討する。
ただし現行スクリプトは `import.meta.url` の親から対象 root を導出して `chdir` する。
Template 側からそのまま起動すると **Template を更新する**ため不採用。
明示的な対象 root 引数などの改修と試験が先に必要になる。
`curl .../master/... | node` や、YAML と異なる可動 ref のスクリプト実行は採用しない。
追加 checkout を更新ブランチの `git add -A` に混ぜないことも条件とする。

### 2.7 ネストと規模

現行の公式上限は、トップの呼び出し側を含む **10 階層**、
すなわち受信側は最大 9 階層。旧い 4 階層の説明は採用しない。
単一 workflow から呼べる一意な reusable workflow はネスト込みで最大 50。
循環は禁止、全段が呼び出し元から参照可能である必要があり、
権限は昇格不可、secrets は各段で明示的に次へ渡す（[S1]・[S2]）。
本案は当面「呼び出し側 → 共通」の 2 階層に限定する。

## 3. 候補比較と採用範囲

| 案 | 修正配布 | 必須チェック名 | 固有差・運用 | 判断 |
| --- | --- | --- | --- | --- |
| A: reusable workflow | 共通 YAML を集約 | 接頭辞が付く | ジョブ・権限・runner も集約可能 | 非必須ジョブ向き |
| B: composite action | step 群を集約 | 外側の job 名を保持可能 | runner・権限・job・イベントは各側に残る | 補助候補 |
| C: コピー + 自動 PR | 修正ごとに各 repo の PR | 現状維持可能 | 差分検出・固有部分の保護が必要 | 必須ジョブ向き |
| D: A + C | 共通ロジックと薄い版更新を分離 | 当面変更不要 | 2 系統の管理は残る | **推奨** |

B は既存のジョブ名を維持でき、スクリプトを action に同梱できる点が強い。
ただし複数ジョブの制御や workflow 全体の保守は残り、
今回の patch 系には A の方が自然である（[S7]）。
composite action 自体には secrets コンテキストが無く、必要な秘密は入力や env で渡す設計になる。

D の C は、共通部分の管理元と許可対象リポジトリを固定し、
Template から各リポジトリへ差分のある更新 PR を出す案とする。
既存 PR があれば重複作成せず、固有ジョブ・パス・ライセンス設定を保持する。
必須チェック名や公開方式までテンプレート文字列置換で揃えない。
生成した差分を CI とレビューへ通し、失敗や衝突は明示して止める。
配布の実装、App 権限、対象 manifest の書式は別 Issue で決める。

| 対象 | 第 1 段階以降の方針 |
| --- | --- |
| patch-updates / patch-updates-sync | A。イベントと concurrency は薄い caller に残す |
| patch-release | A。release-run 入力が互換なリポジトリだけ有効化 |
| pr-issue-link-check | 後続候補。警告版とコメント版を保存してから検討 |
| pr-title-wip-check | C。全リポジトリの必須名 `wip-title` を維持 |
| dependency-review | 当面 C。ライセンス・コメント・権限差を先に整理 |
| 参照ソース取得 | workflow は廃止。C で取得スクリプトと SHA 記録の規約を配る |
| CI / audit / CodeQL / integration / E2E | C。必須名と固有の検査範囲を維持 |
| release-run / release / aks-image | 固有実装を維持。公開認証や配布形式を混ぜない |

## 4. 移行計画

### 第 0 段階: 前提合意と小さな試験

設計レビュー後に別 Issue / PR で行う。**本変更には検証 workflow も追加しない。**
まず Template の公開化を承認・実施できるか決める。
公開しないなら public 側の pilot は止め、C または置き場所変更を選ぶ。
internal の Template 内だけの自己呼び出しでは、public 側の共有可否の検証にはならない。

書込みも秘密も不要な小さな reusable workflow と public caller を用い、
次を試験して実行 URL・SHA・check-runs の名前を記録する。
公開範囲の変更や試験用リポジトリ作成は別途承認の対象とする。

| 試験 | 合格条件 |
| --- | --- |
| public caller → 共通 workflow | 許可設定の下で SHA 固定の呼び出しが成功 |
| 名前と失敗伝播 | `caller / callee` の実名を採取し、試験用ルールセットで失敗時の拒否を確認 |
| 入力・秘密・権限 | 非秘密入力の型を確認。秘密未設定・権限不足は明示的に失敗 |
| checkout | 作業対象が caller、参照元が固定 SHA であることを確認 |
| matrix / skip / cancel | 名前・結論と必須チェックの扱いを確認 |
| 再実行と巻戻し | 同一 SHA の再現性と旧 SHA への復帰を確認 |

秘密を使う試験は無害な試験と分け、専用の最小権限 App で行う。
本番の PR・タグ・公開物を作らず、fork PR に書込み権限や秘密を渡さない。

### 第 1 段階: patch 系 3 本を pilot

public 側 pilot は **CalendarFeed 1 件**を候補とする。
3 本が揃い、release-run の入力が互換で、フロントエンドもあり検出範囲を確認できる。
本番で自動リリースまで無断で起動せず、検証環境で no-op と安全側の分岐から試す。

共通側は既存の定期実行ファイルと区別できる `reusable-patch-*.yml` などの名前にする。
Template 自身の既存 schedule と共通定義の schedule を二重に走らせず、
共通側の入口は `workflow_call` のみにする。
master に確定した SHA を記録してから caller を変更する。
caller と callee の job 名は現行名を使う案とし、想定される新しい check 名は
`patch-updates / patch-updates`、`sync-develop / sync-develop`、
`patch-release / patch-release`。これらの実名は試験で確定し、必須には追加しない。

| 共通 workflow | 最小契約案 | caller に残すもの |
| --- | --- | --- |
| patch-updates | client ID: string、App 秘密鍵: secret | 既存 cron、dispatch、contents: read |
| patch-updates-sync | 同上。PR 情報はイベントから取得 | closed/master のイベント、merged/head 条件 |
| patch-release | 互換な release-run への dispatch に限定 | 既存 cron、dispatch、actions: write |

最初から frontend パス、任意 shell、任意 script URL を入力で受け付けない。
Node 24 と caller の global.json を使い、実行対象の選択権をむやみに広げない。
同期の merge commit、更新 PR の squash、NOTICE 不整合時の停止、
開いた PR がある場合の no-op、master が無い場合の develop 選択を保存する。

patch-release の「patch 以外の変更あり」「タグ無し」「実行中」「release PR あり」の停止も保存する。
入力不一致の 6 リポジトリは、release-run の契約修正を別件として完了するまで対象に加えない。
`bump` 等を削ってタグ作成だけへ dispatch する代替は、採番・版更新の意味を失うため採用しない。

### 第 2 段階: 各リポジトリの置換

各リポジトリでは別 Issue と develop 起点の PR を作り、次の順で少数ずつ展開する。

1. 固定 SHA、workflow の有無、実効ルールセット、App 設定、master 上のスクリプトを再確認する。
2. patch-updates と sync のジョブ本文だけを SHA 固定の caller へ置換する。
3. 入力が互換な AtomFeed・IdentityProvider・Questionnaire へ patch-release も展開する。
4. 非互換 6 件は契約修正後に追加し、元から無い 4 件には patch-release を新設しない。
5. PR の既存必須チェックと試験記録を確認してマージし、通常の master 反映手順も完了する。
6. 定期実行・更新 PR・CI・同期の連鎖を観測し、失敗時は次のリポジトリへの展開を止める。

14 件すべてへ同じ 3 ファイルを機械的に配布しない。
sync の merged PR は master のファイルを使うため、
develop 側だけ caller に替えた状態と master 反映後の状態を区別して確認する。

### 必須チェックを将来 A にする場合の変更順序

pilot の 3 本は現在必須でないので、**ルールセットを変更しない**。
後日必須ジョブを移す場合だけ、次の二重稼働で保護の空白を防ぐ。

1. develop/master 両方の実効ルールセット、integration ID、JSON、同期スクリプトを保存する。
2. 旧チェックを残して、新名の reusable チェックを追加する PR を通す。
3. 実際に現れた check 名と失敗時の拒否を確認し、対象両ブランチへ定義を届ける。
4. 旧名を必須のまま新名も必須にし、両方が成功する移行期間を設ける。
5. 新名の定義が無い既存 PR の更新も済ませ、ルールから旧名だけを外す。
6. 旧ジョブの削除 PR を通す。JSON・Sync-Ruleset・release-run の照合も整合させる。

新チェック未生成の段階で必須にすると全 PR が待ち続ける。
逆に旧チェックを先に削除すると旧名待ちで止まる。
自動マージを一時停止して操作窓を確保し、保護全体の無効化や管理者 bypass を通常手順にしない。
develop だけ更新して master を放置せず、ブランチ別の E2E と出所 App の制限も保存する。

### 戻し方

caller の更新 PR 前に、旧ファイル・旧 SHA・ルールセットを保存する。
pilot の不具合では自動マージと対象の定期実行を止め、
caller を旧 SHA または旧いコピー本文へ戻す revert PR を出す。
無効化した定期実行は、復旧確認後に戻す。force push やタグの付け直しは行わない。
開いた patch / sync PR は人が確認し、既存更新を消すための強制 reset はしない。
dispatch 済みの実行や作成済みタグ・公開済み配布物は YAML を戻しても取り消されない。

必須名を変更済みなら、旧ジョブを新ジョブと並行して先に復旧させる。
旧名の成功を確認してから旧名を再び必須にし、新名の必須設定を外した後で新ジョブを除く。
チェック名を出さないまま保護設定だけ戻さない。

| 固有挙動 | PR コメント版と警告版、依存ライセンス条件を入力既定で変えない |

| 保守責任 | 共通 SHA の承認者、互換性方針、配布 manifest、旧版の保守期限は未決 |
