# 再利用可能なワークフローの棚卸し

[設計メモ](再利用可能なワークフローの設計.md)の根拠資料。Issue #40、参照日 **2026-10-22**。
名前の接頭辞は全件 `vehiclevisionjp/VehicleVision.PleasanterTools.`。以下は末尾だけで表記する。

**2026-10-26 の方針変更（Issue #61）**:
以下の設置数・差分は 2026-10-22 時点の記録であり、現在の配布状況を示さない。
参照更新 workflow は再利用対象から外し、各アプリで削除する。
AI 専用で CI は使わないため、本体は Git で追跡せず `scripts/sync-reference.sh` で必要時に取得する。
再現性は文書の SHA・固定リンク・参照日で担保し、日次の追従 PR や bot の迂回権限は不要。
各アプリへの適用は [配布手順](参照ソースのオンデマンド取得への配布手順.md) に従う。

## 1. 読み取り方法と固定位置

全 14 件のローカル `origin/develop` を `git show` で読み、
GitHub API の `branches/develop` の SHA と比較した。
古いローカル参照は fetch せず、API で得た固定 SHA の tree/blob から内容を補った。
下表の **採用 SHA** は比較に使った GitHub 上の develop の位置。
読み取り中に進む develop の名前ではなく、この SHA の内容を比較した。
他リポジトリの作業ツリー・参照は変更していない。

再取得には次の読み取り専用コマンドを使える。`$repo` は owner/name、`$sha` は上表の値。
`$file` に `.github/workflows/patch-updates.yml` などを指定する。

```powershell
git show origin/develop:.github/workflows/patch-updates.yml
gh api "repos/$repo/branches/develop" --jq .commit.sha
gh api "repos/$repo/git/trees/${sha}?recursive=1"
gh api "repos/$repo/contents/${file}?ref=$sha" --jq .content
gh api "repos/$repo/rulesets?includes_parents=true"
gh api "repos/$repo/rulesets/$id"
gh api "repos/$repo/actions/permissions"
```

contents の `.content` は Base64。tree の blob SHA から `git/blobs/<SHA>` を読む方法でも同じ内容を得られる。
ruleset・公開範囲・Actions 設定はコミットに含まれず、参照日時点の API 応答を根拠とする。
リポジトリの source は `https://github.com/<owner>/<repo>/blob/<SHA>/<file>` で再参照できる。
認証秘密の値は読んでいない。

## 2. リポジトリ別の主要な差

frontend の「同名」は `src/VehicleVision.PleasanterTools.<末尾>.Frontend`。
「なし」は専用 frontend ディレクトリが無い意味であり、ルートの package.json は全件にある。
AtomFeed・CalendarFeed・Questionnaire には `tools/screenshots/package.json` もある。

CodeQL は **全件にファイルがある**。C# だけの構成と、C# + TypeScript の構成を区別する。
「条件付き」は visibility が public または `CODEQL_ENABLED == 'true'` という YAML 上の条件。
「preflight」は事前の advanced_security 判定と summary ジョブを持つ構成。
ファイルがあることは、解析の実行成功を意味しない。

| --- | --- | --- | --- | --- | --- |
| AtomFeed | 同名 | C# + TS、preflight | あり | 採番型 | Web ZIP |
| CalendarFeed | 同名 | C# + TS、preflight | あり | 採番型 | Web ZIP |
| CalendarStyleCreator | なし | C# | なし | なし | 下書き ZIP |

| Questionnaire | 同名 | C# + TS、preflight | あり | 採番型 | Web ZIP |
| Core | なし | C# | なし | なし | NuGet / OIDC |
| BinaryMigrator | なし | C#、条件付き | あり | タグ型 | portable ZIP |
| DatabaseConverter | なし | C#、条件付き | あり | タグ型 | portable ZIP |

この差は YAML の入力では解消できず、公開リポジトリから Template の reusable workflow を直接呼べない。

### 共通候補のファイル単位の実差

下表のファイルは `.github/workflows/` 配下。すべて `.yml`。
「種類」はファイル内容のバイト単位の分類で、機能差のないコメント・引用符の差も含む。

| ファイル（拡張子省略） | 設置数 | 種類 | 実際の差・共通化上の注意 |
| --- | --- | --- | --- |
| patch-updates | 14 | 1 | master の有無を一覧で判定。土台のスクリプトを使う |
| patch-updates-sync | 14 | 1 | master へ patch PR がマージされたら develop へ merge 同期 |
| patch-release | 10 | 1 | 同一でも release-run の入力に非互換がある |
| pr-issue-link-check | 14 | 2 | 5 件がコメント作成・更新、9 件が warning だけ |
| pr-title-wip-check | 14 | 2 | 5 件がイベント title、9 件が API の最新 title |
| dependency-review | 14 | 4 | ライセンス拒否・コメント・条件・timeout・checkout 設定に差 |
| reference-submodule-update（廃止対象） | 13 | 3 | 当時 Core に無し。McpOAuthWrapper が develop 明示 |
| release-run | 10 | 3 | 4 件が採番型、5 件が同一タグ型、1 件が KVS 追加タグ型 |
| release | 14 | 12 | Web / portable ZIP・下書き・NuGet で公開方式が異なる |
| codeql | 14 | 8 | 解析言語・事前判定・summary・条件・ビルド対象に差 |
| dependency-audit | 14 | 7 | npm の探索先、NOTICE 検査の有無、NuGet 手順に差 |
| ci | 14 | 10 | frontend・DB・配置・KVS・SDK・規約などの固有ジョブ |

PR ポリシーと dependency-review の「5 件」は
AtomFeed・CalendarFeed・IdentityProvider・Questionnaire・Core。
この 5 件は dependency-review で拒否ライセンス一覧と PR コメントを設定し、
`pull-requests: write` を要求する。他 9 件へ暗黙に適用すると方針変更になる。
CalendarStyleCreator / IndexCreator、McpOAuthWrapper、
残り 6 件で dependency-review の定義がさらに分かれる。
残り 6 件だけが public / CODEQL_ENABLED の条件を持つ。

dependency-audit の npm-audit は、frontend のある 4 件ではそのディレクトリを対象にし、
`npm audit signatures` も実行する。Core は npm-audit ジョブを持たない。
残る 9 件ではルートの package.json が対象。
NOTICE 専用ジョブは frontend のある 4 件、Core、CalendarStyleCreator、IndexCreator にある。
patch 更新スクリプトの全 package.json 探索とは対象範囲が異なるので、同じ入力で兼用しない。

当時の参照更新には、Questionnaire のコメントの Issue 表記、
McpOAuthWrapper の develop 固定・timeout・サマリなどの差があった。
2026-10-26 の決定で workflow 自体を削除するため、これらの差を共通化する必要は無い。
Core にも workflow は新設しない。必要な事実確認にはオンデマンド取得を使う。

### スクリプトも同一とは限らない

`scripts/apply-patch-updates.mjs` は 13 件が同一、IndexCreator だけ異なる。
IndexCreator ではパッケージ名の検査、版文字列の再構成、NOTICE が無い場合の停止が標準版と異なる。
このメモで修正はしない。移行 PR でスクリプトまで無条件上書きしない。
現行スクリプトの root は自身のファイル位置から求めるため、
Template を別 checkout してそこから起動する案には対象 root の設計変更が必要になる。

### リリースの機能差と入力の互換性

| 分類 | 対象 | 実際の処理 |
| --- | --- | --- |
| 採番型 | AtomFeed / CalendarFeed / IdentityProvider / Questionnaire | plan → run、採番と PR・タグ |
| タグ型 | BinaryMigrator / DatabaseConverter / FeedIngest / MailIngest / Template | 検査後にタグ作成のみ |
| KVS 追加タグ型 | McpOAuthWrapper | タグ型 + Redis / Valkey の検査名照合 |
| 下書き公開 | CalendarStyleCreator / IndexCreator | タグ push、package.ps1、Release を draft 作成 |
| NuGet 公開 | Core / DotNetClient | タグ push、pack、NuGet/login の OIDC で push |

採番型の入力は `bump`（patch/minor/major）・`dry_run`・`acknowledge`。
`release-next-version.sh` と `release-run.sh` を使い、develop の CI を調べて処理を進める。
タグ型の入力は `release_tag`・`dry_run` だけ。
`release-check.ps1` と check-runs の名前一覧を使い、実タグ作成は master から要求する。
McpOAuthWrapper は KVS の日本語チェック名も照合する。
この照合名は ruleset の必須名とは別の結合点として扱う。

**同一の patch-release は `--ref develop -f bump=patch -f dry_run=false -f acknowledge=true`
を送るため、タグ型の 6 件と契約が一致しない。**
存在チェックだけでは互換性を判断できない。
GitHub 上で実際にどの応答となるかは未確認であり、正常動作したとは記載しない。
自動リリースの pilot は採番型に限定し、非互換修正は別 Issue でレビューする。

Web ZIP の 4 件はそれぞれの `.Web` を publish し、
frontend・ライセンス文書を含む配置物と SHA-256 を GitHub Release へ公開する。
IdentityProvider と Questionnaire は App_Data の同梱もある。
portable ZIP の 6 件は package.ps1 / release-check.ps1 を使うが、
製品名・案内文・ライセンス文書が異なる。McpOAuthWrapper は npm run check も実行する。
Core / DotNetClient の OIDC は workflow 名などの信頼ポリシーも別途確認が必要であり、
ZIP の共通化と同時には変更しない。

## 3. 適用中の必須チェック

Git 内の ruleset JSON の既定値ではなく、
`rulesets?includes_parents=true` と各 ID の詳細 API から取得した **active** な設定。
全件に develop-protection / master-protection / release-tag-protection がある。
両ブランチとも strict は false。タグ用には status checks は無い。
branch protection API の旧形式ルールを含めた追加制約の有無は未確認。

長い名前を省略せず残すため、下表の略号を定義する。

| 略号 | 完全なチェック名の集合 |
| --- | --- |
| B | `build-test`、`instructions`、`nuget-audit`、`npm-audit`、`wip-title` |
| W | `build-test`、`frontend`、`license-check`、`wip-title`、`notice-consistency`、`integration` |
| K | `build-test`、`sdk-consistency`、`instructions-sync`、`wip-title`、`notice-consistency`、`integration` |
| A | `Analyze (csharp)` |
| N | `notice-consistency` |
| I | `integration` |
| E | `e2e / pleasanter`、`e2e / saml` |

`+` は集合への追加。出所欄の 15368 は GitHub Actions の integration ID。
「未指定」は取得した required_status_checks 要素に integration_id が無いこと。

| 末尾 | develop の必須集合 | master の必須集合 | 出所 |
| --- | --- | --- | --- |
| AtomFeed | W + E | W | 全件 15368 |
| CalendarFeed | W + E | W | 全件 15368 |
| CalendarStyleCreator | B + N + A | B + N + A | 未指定 |
| IdentityProvider | W | W | 全件 15368 |
| IndexCreator | B + N + A | B + N + A | 未指定 |
| McpOAuthWrapper | B + A | B + A | 未指定 |
| Questionnaire | W + `e2e` | W | 全件 15368 |
| Core | K | K | integration のみ未指定、他は 15368 |
| BinaryMigrator | B + A | B + A | 未指定 |
| DatabaseConverter | B + I + A | B + I + A | 未指定 |
| DotNetClient | B + A | B + A | 未指定 |
| FeedIngest | B + A | B + A | 未指定 |
| MailIngest | B + `cla` + A | B + `cla` + A | 未指定 |
| Template | B | B | 未指定 |

`wip-title` は全件で必須。
patch-updates / sync-develop / patch-release、issue-link、dependency-review、
reference 更新、release-run はこの一覧には含まれない。
CodeQL の YAML があっても必須チェック A が付くとは限らない。
CodeQL を共通化するなら、現状の実行条件と必須要件の両方を別々に確認する。

Git 上には ruleset JSON が無いリポジトリや旧 protected-branches.json の残るものがあり、
API 上の統一済みの設定と一致しない。
Template / FeedIngest / MailIngest の JSON にも、
API 側で加わった CodeQL・CLA 等の必須チェックがすべて表現されているわけではない。
再配布で live の必須チェックを既定値へ戻さないこと。

この棚卸しは定義と設定の読み取りだけであり、
現行の全ワークフローが成功すること・自動リリースの動作・
共有後の check 名と権限の実効動作は **未確認**。
