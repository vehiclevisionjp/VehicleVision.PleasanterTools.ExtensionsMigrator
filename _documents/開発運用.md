# 開発運用

## ブランチと PR

- `develop` が開発の本流、`master` がリリース確定用
- 作業ブランチは `develop` から分岐し、PR の base も `develop`
- Issue を作ってから変更し、PR 本文に `Closes #N` を書く
- 作業中は Draft とし、タイトルに `WIP:` を付ける。Draft 解除はレビュー可能、`WIP:` 除去はマージ可能の合図

## 定期実行

| 対象 | 頻度 | 仕組み |
| --- | --- | --- |
| npm・NuGet の patch 更新 | 毎日 2 回（09:00 / 21:00 JST） | `patch-updates.yml` が最新 patch を適用して `master` へ PR を作り、必須チェックが通れば自動マージ。続けて `patch-updates-sync.yml` が `master` → `develop` の同期 PR を作り自動マージ |
| Actions の更新 | 毎週 | Dependabot（`.github/dependabot.yml`）が `develop` 向けに PR を作る |
| 依存の脆弱性検査 | 毎週月曜と push | `dependency-audit.yml` |
| CodeQL と依存レビュー | 毎週日曜と push／PR | `codeql.yml`、`dependency-review.yml`。public か GHAS 有効のリポジトリだけで動く（下記） |

Pleasanter 本体は AI の事実確認専用で CI は使わない。
参照前に `bash scripts/sync-reference.sh` で上流 `main` の先頭を取得する。
既定は `_reference/Implem.Pleasanter`、共有先は `PLEASANTER_REFERENCE_DIR`。
Git で追跡せず、日次の更新 workflow・追従 Issue / Draft PR・bot の迂回権限は不要。
文書の再現性は、確認した SHA・ソースへの固定リンク・参照日で担保する。
過去の記述は再確認してから更新する（[参照ソース](../_reference/README.md)）。
各アプリへの移行は [配布手順](参照ソースのオンデマンド取得への配布手順.md) に従い、個別の Issue / PR で行う。
Manual・Overview の参照用サブモジュールも、同日の決定（Issue #63）で非追跡へ移行する。
各アプリは一覧なしの既定 1 件を維持し、Manual・Overview は `references.json` の一覧を使う。
一覧は `--manifest <path>`、取得の基点は `--root <dir>` で変更できる。
一覧があるとき `PLEASANTER_REFERENCE_DIR` は無視する。JSON の解析は jq、node、python の順に選ぶ。
private は取得する人の Git 資格情報または `gh auth login` の認証を使い、bot の App は使わない。
取得できない private は警告とし、未確認の事実を補わない。入力不正・ローカル変更などは失敗にする。
Template の変更だけでは配布済みとしない。参照先ごとのライセンスとビルド・配布の隔離も維持する。

## GitHub の初期設定

新しいリポジトリを作った直後に行う。

1. 既定ブランチを `develop` にする
2. **リポジトリの設定を、全リポジトリと同じにする。** 定義は `.github/repo-settings.json`、反映は `./scripts/Sync-RepoSettings.ps1`（管理者権限が要る）。
   マージ後にブランチを削除する・自動マージを許可する・ブランチ更新のボタンを出す。マージ方式は squash と merge commit だけ（rebase は使わない）。
   Wiki・Projects・Discussions は使わない（内容は `_documents` に置く）。依存グラフと Dependabot アラートも有効にする
   （無いと依存レビュー `dependency-review` が失敗する）。**public** のリポジトリでは、シークレットスキャン・プッシュ保護・
   Dependabot のセキュリティ更新は**使わない**（patch 更新は自前のワークフローで行う）。シークレットスキャンとプッシュ保護は、internal / private では GitHub Advanced Security が要るので対象外
3. **ルールセットを設定する。** 定義は `.github/rulesets/` の 3 つ、反映は `./scripts/Sync-Ruleset.ps1`（管理者権限が要る）。
   全リポジトリで同じ形にしている（2026-10-20 に統一した）。リポジトリの管理者は迂回できる（初期配置と緊急対応のため）
    - `develop-protection`: develop。削除と強制 push を禁止し、必須チェックを要求する
    - `master-protection`: master。上に加えて PR を要求する
    - `release-tag-protection`: タグ `v*`。削除と強制 push を禁止する
    - 必須チェックの既定は `build-test`、`instructions`、`nuget-audit`、`npm-audit`、`wip-title`。
      公開リポジトリでは、下記のブートストラップ条件を満たすブランチに `cla` も要求する。
      **すべての必須チェックの発行元を GitHub Actions（`integration_id: 15368`）へ固定する。**
      必須チェックと同じ名前を他の App が名乗り、チェックをすり抜けることを防ぐため
      （2026-10-22 決定）。`cla` も JSON に定義する。
      CodeQL を動かすリポジトリでは `-IncludeCodeQL` で `Analyze (csharp)` も必須にする。
      そのリポジトリ固有のジョブ（例: `integration`）は `-ExtraChecks` で足す（**CI のジョブ名と同じ文字列**）。
      `cla` の個別指定は不要。旧い `-ExtraChecks cla` は警告して無視し、二重定義や対象外への追加を防ぐ。
      追加チェックと CodeQL も同じ App 固定にする。同期と監査の期待値は、
      `RepoAudit.psm1` の `Get-AuditExpectedRuleset` で生成する。
      存在しないチェックを必須にすると、その結果を待つ PR が永遠に止まるため、
      基準のジョブが無いリポジトリでは `.github/audited-repos.json` に任意の `omitChecks`（文字列配列）を書く。
      例: Core は `["instructions", "npm-audit"]`、AtomFeed などは `["instructions"]`。
      同期時は同じ値を `-OmitChecks instructions,npm-audit` のように渡す。
      `-ExtraChecks` と `-OmitChecks` はカンマ区切りの 1 文字列も分割し、前後の空白を除く。
      基準 JSON に無い名前（誤字・追加チェック・CodeQL など）の除外指定はエラーにする。
      除外対象を `-ExtraChecks` にも指定した場合は除外を優先する。
      `cla` の除外指定は無視し、公開範囲・理由付き例外・前提ファイルによる既存の判定を変えない。
      App 指定なし（省略・null）や別 App（例: CodeQL App ID `57789`）は、監査で差として報告する。
      **必須にしないと、失敗してもマージできてしまう**
    - `-WhatIf` は GET と反映予定 JSON の表示だけで、作成・更新・削除をしない。
      `master` がまだ無い場合、そのルールセットは作成・更新しない
    - **ルールセットの JSON と `Sync-Ruleset.ps1` の正本は Template だけにある。** 他のリポジトリへは複写せず、
      Template の作業ツリーから `-Repository owner/name` を付けて反映する（`Sync-Ruleset.ps1` は実行したリポジトリの
      `.github/rulesets/` を読む）。旧い複写（`protected-branches.json`、`cla` と App 固定が無い 3 分割の JSON、
      旧い `Sync-Ruleset.ps1`・`Sync-RepoSettings.ps1`）が残るリポジトリでその場で実行すると、`cla` と App 固定が外れる。
      旧い複写は見つけ次第削除する。差は監査（`Test-RepoAudit.ps1`）で確認する
    - 旧い形（develop と master を 1 つにまとめた「保護ブランチ」）が残っていれば、スクリプトが新しい 3 つを作ってから消す
4. patch 更新など既存の自動化に GitHub App を使う。
   リポジトリ変数 `MY_REPO_AUTOMATION_BOT_CLIENT_ID` と
   シークレット `MY_REPO_AUTOMATION_BOT_PRIVATE_KEY` を登録する。
   patch 更新には Contents・Pull requests の書き込み権限が要る。
   参照ソースの取得には App・Issue 作成権限・ルールセット迂回は不要。
   他用途の資格情報は削除しない。既存設定の変更は承認済みの別作業で行う
5. 公開範囲に応じて CodeQL と依存レビューを切り替える。**public** のリポジトリは何もしなくてよい。**internal / private** は、コードスキャンと依存レビューに GitHub Advanced Security（GHAS）が要る。GHAS を有効にしたら、リポジトリ変数 `CODEQL_ENABLED` を `true` にする（`gh variable set CODEQL_ENABLED --body true`）。有効にしない間、この 2 つのジョブはスキップされ、リリースの確認もスキップを許容する
6. ラベルを作る。定義は `.github/labels.json`、
   反映は `./scripts/Sync-Labels.ps1`（gh CLI でログイン済みであること）。
   参照ソース取得は Issue やラベルを使わないが、他用途のラベルは維持する
7. 「Template repository」にするのはテンプレート側のみ。派生したリポジトリでは外す

## 公開リポジトリの CLA

**公開するリポジトリは、現在のライセンスを問わず CLA を必須にする。**
既定の提供条件は AGPL と商用のデュアル。AGPL 単独、LGPL でも同じ。
他人の著作物を商用ライセンスで再頒布する権利は、本人から許諾を受けない限り得られない。
公開時点から貢献の再許諾を確認し、商用ライセンスでも提供できる状態を保つ。

internal の Template 自身は対象外。Template の GitHub ルールセットへ `cla` を追加しない。
ただし新規公開リポジトリへ配るため、[CLA](../CLA.md)、[貢献手順](../CONTRIBUTING.md)、
[ライセンス説明](../LICENSING.md)、署名用 Issue フォーム、ワークフロー、空の署名一覧を同梱する。
ワークフローは公開リポジトリでだけ実行する。追加の実行スクリプトや外部 CLA サービスは使わない。
名前・許諾先法人と実際の提供ライセンスも確認する。固有部分の選び方は [ライセンス](ライセンス.md) の「正本の使い方」に従う。

### ブートストラップ（必須化より先に配置する）

`cla` は **PR の base コミット**の `.github/cla/signed.yml` を読む。
PR 内で一覧を書き換えても、その PR 自体の署名判定には使わない。
base に一覧が無いとチェックが通らないため、ブランチごとに次の順序を守る。

1. `.github/workflows/cla-check.yml` と `.github/cla/signed.yml` を `develop` に配置する。
   初期一覧は `signatories: []`。必要な署名は下記の管理者手順で確認する
2. `master` が存在する場合も、**先に両ファイルを master へ反映する**。
   develop が準備済みでも、初回の develop → master の PR に `cla` を先に要求しない
3. `Sync-Ruleset.ps1 -Repository owner/name -WhatIf` で反映予定を確認する。
   スクリプトはブランチ一覧の SHA に固定し、各ブランチの両ファイルを `gh api` の GET で確認する。
   監査と同じ Git Trees API を使い、通常ファイルの存在を判定する。ツリーの打ち切りはエラーにする。
   片方でも無ければ警告して、そのブランチの `cla` 必須化だけを保留する。
   403・通信障害などの取得エラーでは、反映開始前に停止する
4. 管理者が承認済みの別作業として `-WhatIf` を外して同期する。
   未配置ブランチはファイル反映後に再同期する。`master` が無ければ、そのルールセットは作らない

**`cla` は `develop-protection` と `master-protection` の両方に定義する。** `cla-check.yml` は
`develop` と `master` を base にした PR で動くため（`pull_request_target` の `branches`）、
`master` 向けの PR（develop → master のリリース PR を含む）にも署名の確認が走る。
`master` に必須化しない理由は無く、外れているのは前提ファイルが未配置のブートストラップ中か、同期の漏れだけである。
同期漏れは監査の「master cla 必須」の差として現れる。

既存の `cla` ワークフローが動いているブランチでは、必須化を保留してもワークフロー自体は止めない。
この手順は初期配置で PR が行き詰まらないためのもの。未署名の貢献を取り込んでよいという例外ではない。

### 管理者による署名の追記

1. 貢献者が「CLA への署名」の Issue で、対象の CLA への同意を表明する。
   管理者はログイン名・本人の同意・許諾権限を確認する。
   業務としての貢献なら、法人用の同意と法人を代表する権限も確認する
2. 管理者が対象リポジトリの署名一覧へ追記する。最初の署名時は `signatories: []` を
   `signatories:` と `- login:` のブロック形式に変更し、`login`・`issue`（同意した Issue の番号）・
   `signed_at`（確認日）を記録する。**未確認の署名者を登録しない**。秘密情報は書かない
3. 管理者の Issue / PR として一覧の変更を反映する。初回で署名確認 PR 自体が止まる場合は、
   管理者が同意を確認したうえで既存の管理者 bypass を使う（チェックを無効化しない）
4. 貢献 PR の対象 base に一覧が入った後、PR を更新するか Actions を再実行する。
   develop と master の一覧は別々に確認し、必要に応じて通常の PR で同期する

確認対象は PR 作者のログイン名。共同著作者全員の権利を自動確認するものではなく、
管理者は取り込み時に実際の貢献の権利も確認する。
bot の除外は `dependabot[bot]`・`github-actions[bot]`・`my-repo-automation-bot[bot]` の完全一致のみ。
bot もジョブを省略せず成功を報告する。未知の bot は自動除外せず、用途と著作者の有無を確認して見直す。

### 基準と既存設定の差

CLA の宣言は `.github/audited-repos.json` の `visibility` から決める。
**public なら `requireCla=true`、internal / private なら false が既定**で、各リポジトリに重複記載しない。
例外が必要な場合だけ `requireCla`（bool）と `claReason`（理由）を書く。
同期時も `-RequireCla:$false` などで同じ例外を指定する。
非公開で CLA を運用する例外では、ワークフローの公開範囲条件も別途調整する。

2026-10-22 に Questionnaire と MailIngest の実際のルールセットを GET で確認した。
Questionnaire は既存チェックを GitHub Actions の App ID `15368` に固定しているが、`cla` は未必須。
MailIngest は `cla` を含むが App 指定は無い。
2026-10-22 の決定により、新基準では `cla` だけでなく、すべての必須チェックを Actions に固定する。
既存との差は監査で報告し、この基準整備だけで他リポジトリの設定を変更しない。

## 共通設定の読み取り専用監査

`pwsh scripts/Test-RepoAudit.ps1` は対象の GitHub 設定を変更せず、差分を Markdown 表に出す。
機械可読の結果は既定で `temp/repo-audit.json` に保存する。
週に一度、新しいリポジトリの追加後、共通定義や同期スクリプトの変更前後に回す。
検出した差分は自動修復しない。監査をマージ必須チェックにはせず、外部の設定差で通常の PR を止めない。

前提は PowerShell 7・Git・GitHub CLI（`gh auth login` 済み）と、GitHub / nuget.org への接続。
書き込み権限は要求せず、GitHub への要求はすべて GET。
public の情報は通常の読み取り API を使い、認証が使えない場合も公開情報は匿名 GET で再試行する。
internal / private の Contents、設定、Actions の Variables / Secrets などは、それぞれ読み取り権限が必要。
読み取り権限だけでは見えない管理項目もあるため、監査結果が「確認不可」になることはある。

```powershell
# Markdown は標準出力、JSON は temp/repo-audit.json
pwsh scripts/Test-RepoAudit.ps1

# 保存先を指定する場合、親ディレクトリは先に作る
pwsh scripts/Test-RepoAudit.ps1 `
  -JsonPath temp/audit.json `
  -MarkdownPath temp/audit.md

# ネットワークを使わない回帰テスト（CI の instructions でも実行）
pwsh scripts/Test-RepoAuditLogic.ps1
```

終了コードは **0: 全対象が一致、1: 差分・欠落・確認不可・取得エラーあり、2: 基準不正や実行失敗**。
CI では終了コードと JSON の `results[].status` の両方を見て、差分と権限不足を区別する。
`unknown` は一致ではない。403 / 404 は権限による非表示もあるため、一覧を取得できない場合に
「無い」とは断定しない。レート制限や通信障害は `error` として出す。
実行中に予期しない例外で中断した場合は、部分結果を成功として保存しない（終了コード 2）。

### 基準と比較の範囲

基準は **実行元 Template のローカル作業ツリー**。未コミット変更も含むため、
正式な記録はクリーンなコミットで実行し、結果の `baselineCommit` とブランチの SHA を残す。
共通ファイルと依存は、ブランチ一覧から取得したコミットに固定して読む。
GitHub の設定 API 自体には一括スナップショットが無いため、監査中の設定変更には注意する。

| 項目 | 基準・判定 |
| --- | --- |
| リポジトリ設定 | `.github/repo-settings.json` の全項目と、設定ファイルの公開範囲 |
| セキュリティ | public の設定を JSON と比較。Dependabot alerts は `Sync-RepoSettings.ps1` と同じく有効を要求 |
| ルールセット | `.github/rulesets/*.json` の 3 本。対象 ref・有効状態・ルール・マージ方式・bypass を比較 |
| 必須チェック | 同期と同じ関数で omitChecks を除外し、CodeQL・ExtraChecks を追加。公開範囲と前提ファイルで `cla` を判定 |
| CLA | develop・master のワークフローと署名一覧の存在、準備済みブランチの `cla` 必須化を確認 |
| ラベル | `.github/labels.json` の名前・色・説明。Dependabot と GitHub 初期ラベルは許可リストで除外 |
| Actions | App の変数・シークレットの名前だけ。repository と、そのリポジトリが継承する organization を確認 |
| 共通ファイル | 設定に列挙した 6 ワークフローと patch 更新・参照取得スクリプト、C# の editorconfig 節、ビルドの規約強制 |
| Core の依存 | 両ブランチの csproj にある Core.Data / Core.Mail / Core.Web と、nuget.org の最新の掲載版 |

公開範囲で対象を決めるセキュリティ設定は `Sync-RepoSettings.ps1` と揃え、
internal / private の public 専用設定は「対象外」にする。
Dependabot alerts の有効化は依存グラフを有効にする既存同期の手段であり、同じ API を確認する。
依存グラフだけを独立に照会できる REST API ではないため、表示名も両者を併記している。

ルールの配列順、API のメタデータ、GitHub が補う既定値は無視するが、
必須チェックの追加・欠落・重複や App 固定、非既定のパラメーターは差として出す。
`bypass_actors` が権限で返らない場合は、他の内容を比較しつつ bypass は「確認不可」にする。
追加・継承された基準外のルールセットも報告する。

共通ファイルは `develop` と、存在する場合は `master` を調べる。
CLA の２ファイルも同じブランチ SHA のツリーで存在を確認する（署名者・内容の一致は要求しない）。
前提の欠落は `missing`、読み取り不能は `unknown` / `error` とし、監査は失敗扱いにする。
欠落ブランチの `cla` 必須化はブートストラップ中として対象外にするが、前提の欠落を一致にはしない。
準備済みブランチでは `cla` の欠落・重複・発行 App の違いも差にする。Template の CLA は対象外。
`master` が無い場合、そのルールセットとブランチファイルは対象外。
改行コードを正規化し、**完全一致 / 宣言した置換で一致 / 差あり / 無い**を区別する。
既定の置換は各リポジトリ名から Template 名への置換だけ。
追加の置換はリポジトリごとの `replacements` に「実際の文字列: 基準の文字列」で宣言できる。
対象外は `notApplicableFiles` にパスと理由を明記する。存在しないことから自動的に対象外にはしない。
`.editorconfig` は `[*.cs]` 節だけ、`Directory.Build.props` は
`EnforceCodeStyleInBuild` の定義（重複・条件も含む）だけを比較する。
差分プレビューは最初の最大 6 行の位置と行内容の SHA-256 の先頭 12 桁を出し、本文は出さない。

Actions は `MY_REPO_AUTOMATION_BOT_CLIENT_ID` と
`MY_REPO_AUTOMATION_BOT_PRIVATE_KEY` の存在だけを判定し、値の取得・復号はしない。
変数一覧 API 自体は値を含むため、`gh --jq` 内で名前だけに射影し、監査プロセスへ値を渡さない。
`GH_DEBUG` は子プロセスから外し、API の応答本文・標準エラー・認証情報をログへ出さない。
どちらかのスコープで名前を確認できれば存在、両方の一覧を取得して無い場合だけ欠落にする。
environment に限定された資格情報は、共通ワークフローが environment を指定しないため対象外。

Core の最新版は NuGet の service index から registration API を見つけ、掲載中の版を
SemVer 順に比較する。**preview も含む**（Core がプレリリースを配布しているため）。
直接の版、`VersionOverride`、最寄りの祖先の props 内の単純なプロパティ、中央パッケージ管理を読む。
任意の MSBuild import・条件分岐・浮動版・版範囲は評価せず、固定版を解決できなければ確認不可。
プロジェクトを実行・ビルドして値を得ることはしない。

### 差分を見つけたとき

1. JSON の項目とブランチ SHA を使い、`gh api --method GET` または `git show` で実際の差を確認する。
   Actions の確認も名前の一覧だけにし、シークレットや変数の値を表示しない。
2. 意図した差なら、まず `.github/audited-repos.json` の追加チェック・CLA・公開範囲・対象外理由をレビューする。
   食い違いを隠すために、実際の値をそのまま期待値へコピーしない。
3. 設定を直す場合は別の承認済み作業として、管理者が `Sync-RepoSettings.ps1 -Repository owner/name`、
   `Sync-Ruleset.ps1 -Repository owner/name -IncludeCodeQL -ExtraChecks ...`、
   `Sync-Labels.ps1 -Repository owner/name` を実行する。CodeQL・追加チェック・`-OmitChecks` は監査設定に合わせる。
   `cla` は公開範囲と前提ファイルから自動判定するので、`-ExtraChecks` に渡さない。
   公開範囲の既定と異なる例外がある場合だけ、理由を監査設定に残して `-RequireCla` を指定する。
4. 共通ファイルは各リポジトリで通常の Issue / PR を通して反映し、Core の依存更新も各 CI で確認する。
   App の資格情報が欠落している場合は、管理者が安全な設定経路で登録する。監査は登録しない。
5. 再実行し、結果と終了コードを保存する。

基準を変えるときは Issue を作り、Template の JSON または共通ファイルを PR で更新する。
同期の引数・意味を変える場合は監査の期待値生成と固定入力テストも同じ PR で更新する。
新しいリポジトリは `repositories` に追加し、CodeQL・追加必須チェック・公開範囲を明記する。
CLA は公開範囲の既定を使い、例外だけ理由とともに記載する。
Overview / Manual の除外も同じ設定ファイルで明示している。

## patch 更新の自動適用

- 対象は同じ major.minor の最新の安定版だけ（minor・major は人が見る）。プレリリース版と非推奨の版は選ばない。
- 検出と適用は `scripts/apply-patch-updates.mjs`。版・ロックファイル・NOTICE を 1 つの PR に揃える。`--dry-run` で検出だけ試せる。
- PR と push は `my-repo-automation-bot`（GitHub App）のトークンで行う。`GITHUB_TOKEN` だと CI が動かず、必須チェックが付かないため。
  変数 `MY_REPO_AUTOMATION_BOT_CLIENT_ID` とシークレット `MY_REPO_AUTOMATION_BOT_PRIVATE_KEY` が要る（権限は contents と pull-requests の書き込みのみ）。
- 前回の PR が開いたままなら、新しい PR は作らない。CI が落ちたら自動マージされず PR が残るので、人が見る。NOTICE が自動で直せないときは PR を作らずに失敗する。
- 更新したくない依存は `.github/patch-updates-ignore.txt` に 1 行 1 名で書く（`#` から行末はコメント）。
- 前提: リポジトリの設定で自動マージ（`allow_auto_merge`）を許可し、`master` の必須チェックを設定してあること。

## patch 更新だけが溜まったときの自動リリース

- `patch-release.yml` が、毎日 2 回（11:00 / 23:00 JST。patch 更新の 2 時間後）、最後の安定版タグ以降の `develop` を調べる。
- patch 更新のコミットが 1 件以上あり、**それ以外のコミットが無い**ときだけ、`release-run.yml` を `patch`・`dry_run=false`・`acknowledge=true` で起動する。
  採番・版の引き上げ・`develop` → `master` の PR・タグ付けは、`release-run.yml` が行う。
- 差分が無ければ何もしない。人が入れた未リリースの変更が混ざっているときも自動では出さない（人が内容を見て手で起動する）。
- 動かない条件: 安定版のタグがまだ無い（最初のリリースは人が行う）、`release-run.yml` が無い、リリースが実行中・PR が開いたまま。
- 自動リリースの対象外: Core（プレリリース版のタグ）、IndexCreator・CalendarStyleCreator（`release-run.yml` が無い）。
