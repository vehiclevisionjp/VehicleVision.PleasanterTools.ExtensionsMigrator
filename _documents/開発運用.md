# 開発運用

## ブランチと PR

- `develop` が開発の本流、`master` がリリース確定用
- 作業ブランチは `develop` から分岐し、PR の base も `develop`
- Issue を作ってから変更し、PR 本文に `Closes #N` を書く
- 作業中は Draft とし、タイトルに `WIP:` を付ける。Draft 解除はレビュー可能、`WIP:` 除去はマージ可能の合図

## 定期実行

| 対象 | 頻度 | 仕組み |
| --- | --- | --- |
| npm・NuGet の patch 更新 | 毎日 2 回（09:00 / 21:00 JST） | `patch-updates.yml` が最新 patch を適用して `master` へ PR を作り、必須チェックが通れば自動マージ。続けて `patch-updates-sync.yml` が `master` → `develop` の同期 PR を作り自動マージ |
| Actions の更新 | 毎週 | Dependabot（`.github/dependabot.yml`）が `develop` 向けに PR を作る |
| 依存の脆弱性検査 | 毎週月曜と push | `dependency-audit.yml` |
| CodeQL と依存レビュー | 毎週日曜と push／PR | `codeql.yml`、`dependency-review.yml`。public か GHAS 有効のリポジトリだけで動く（下記） |

Pleasanter 本体は AI の事実確認専用で CI は使わない。
参照前に `bash scripts/sync-reference.sh` で上流 `main` の先頭を取得する。
既定は `_reference/Implem.Pleasanter`、共有先は `PLEASANTER_REFERENCE_DIR`。
Git で追跡せず、日次の更新 workflow・追従 Issue / Draft PR・bot の迂回権限は不要。
文書の再現性は、確認した SHA・ソースへの固定リンク・参照日で担保する。
過去の記述は再確認してから更新する（[参照ソース](../_reference/README.md)）。

## GitHub の設定

設定の正本（`repo-settings.json`・ルールセット JSON・ラベル定義・同期スクリプト）は Template にある。
**このリポジトリへ複写せず**、Template の作業ツリーから `-Repository vehiclevisionjp/VehicleVision.PleasanterTools.ExtensionsMigrator` を付けて反映する
（定義と手順は Template の `_documents/開発運用.md`）。ラベルだけは `scripts/Sync-Labels.ps1` をこのリポジトリに置いている。

- 既定ブランチは `develop`
- リポジトリの設定: `Sync-RepoSettings.ps1`（管理者権限が要る）
- ルールセット: `Sync-Ruleset.ps1`（`develop-protection`・`master-protection`・`release-tag-protection`）。必須チェックは `build-test`・`instructions`・`nuget-audit`・`npm-audit`・`wip-title`（発行元は GitHub Actions に固定）。
  公開後は `cla` も必須にする。`master` はまだ無いので、そのルールセットは `master` ができてから作る
- ラベル: `Sync-Labels.ps1`
- 参照ソース更新・patch 更新に使う GitHub App 用の Variable `MY_REPO_AUTOMATION_BOT_CLIENT_ID` と Secret `MY_REPO_AUTOMATION_BOT_PRIVATE_KEY` は、
  リポジトリの管理者が安全な経路で登録する（値をチャット・Issue・コミットに書かない）
- CodeQL と依存レビュー: public では何もしなくてよい。internal の間は GHAS が無いのでスキップされる

## 公開リポジトリの CLA

公開するリポジトリは CLA を必須にする（[CLA](../CLA.md)）。`cla` は PR の base コミットの `.github/cla/signed.yml` を読むため、
`.github/workflows/cla-check.yml` と `.github/cla/signed.yml`（初期は `signatories: []`）を、`develop` と、存在すれば `master` に先に置く。
署名の確認と追記は管理者が行う。署名の効力はこのツールに対するもので、他のツールには及ばない。詳細は Template の `_documents/開発運用.md`。

## 外部記憶

Claude や Codex が作業の知見を残す必要があるときは、個別のリポジトリを作らず、Internal リポジトリ `VehicleVision.PleasanterTools.ClaudeMemory` に `<ツール名>/` フォルダを作って管理する（運用は同リポジトリの README.md）。本体リポジトリへ記憶ファイルを置かない。

- 作ったら `CLAUDE.md` に URL を書く
- 作業ツリーはエージェントのメモリディレクトリそのものにし、別の clone を作らない（2 つあると片方が古くなる）
- 正式な規約の置き場所ではない。`.github/copilot-instructions.md` が常に優先され、食い違ったら記憶側を直す

## patch 更新の自動適用

- 対象は同じ major.minor の最新の安定版だけ（minor・major は人が見る）。プレリリース版と非推奨の版は選ばない。
- 検出と適用は `scripts/apply-patch-updates.mjs`。版・ロックファイル・NOTICE を 1 つの PR に揃える。`--dry-run` で検出だけ試せる。
- PR と push は `my-repo-automation-bot`（GitHub App）のトークンで行う。`GITHUB_TOKEN` だと CI が動かず、必須チェックが付かないため。
  変数 `MY_REPO_AUTOMATION_BOT_CLIENT_ID` とシークレット `MY_REPO_AUTOMATION_BOT_PRIVATE_KEY` が要る（権限は contents と pull-requests の書き込みのみ）。
- 前回の PR が開いたままなら、新しい PR は作らない。CI が落ちたら自動マージされず PR が残るので、人が見る。NOTICE が自動で直せないときは PR を作らずに失敗する。
- 更新したくない依存は `.github/patch-updates-ignore.txt` に 1 行 1 名で書く（`#` から行末はコメント）。
- 前提: リポジトリの設定で自動マージ（`allow_auto_merge`）を許可し、`master` の必須チェックを設定してあること。

## patch 更新の自動リリースは行わない

- 以前あった `patch-release.yml`（patch 更新だけが溜まったら `release-run.yml` を自動で起動する）は、#39 で削除した。
  nuget.org へ公開した版は取り消せないため、リリースは必ず人が `release-run.yml` を起動する（[リリース手順](リリース手順.md)）。
- patch 更新の PR は従来どおり自動で `master` と `develop` へ入る。未リリースのまま溜まるので、まとめて人がリリースする。
