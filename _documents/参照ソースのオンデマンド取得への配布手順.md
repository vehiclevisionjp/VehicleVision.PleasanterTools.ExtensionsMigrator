# 参照ソースのオンデマンド取得への配布手順

Issue #61・#63、2026-10-26 の決定に基づく **1 リポジトリ分** の手順。
この変更では Template だけを変更する。以下の各アプリへの配布は別作業とし、実施済みとは扱わない。

## 対象と変更の境界

`vehiclevisionjp/VehicleVision.PleasanterTools.` に次の末尾を付けた 13 リポジトリが対象。

AtomFeed・CalendarFeed・CalendarStyleCreator・IdentityProvider・IndexCreator・McpOAuthWrapper・
Questionnaire・Core・BinaryMigrator・DatabaseConverter・DotNetClient・FeedIngest・MailIngest。

加えて Manual・Overview の参照用サブモジュールも対象とする。
各アプリは一覧なしの本体 1 件を維持し、Manual・Overview だけ `references.json` の一覧へ移行する。
一覧の仕様・認証・取得結果の読み方は [参照ソース](../_reference/README.md) を参照する。

本体ソースは AI（Claude・Copilot・Codex）の事実確認専用で CI は使わない。
上流 `main` を必要時に取得し、文書の SHA・固定リンク・参照日で再現性を保つ。
日次追従、ポインタ更新 PR、参照更新用 bot の迂回権限は不要。
GitHub の設定・ルールセット・App・資格情報・ラベルは変更しない。
patch 更新など他用途の bot は残す。マージは行わずレビューを待つ。

## 1. 差を調べて Issue と作業ブランチを作る

対象リポジトリのクリーンな clone で PowerShell から実行する。
例の AtomFeed は対象の末尾に置き換える。一度に 1 リポジトリだけを処理する。

```powershell
$repo = 'vehiclevisionjp/VehicleVision.PleasanterTools.AtomFeed'
git status --short
git fetch origin develop
gh issue create --repo $repo --title '参照ソースをオンデマンド取得へ切り替える' `
  --body 'vehiclevisionjp/VehicleVision.PleasanterTools.Template#61 の決定を反映する。GitHub 設定は変更しない。'
$issue = <作成したIssue番号>
git switch -c "feature/reference-on-demand-$issue" origin/develop
git ls-files --stage -- .gitmodules _reference
git config -f .gitmodules --get-regexp '^submodule\.'
rg -n --hidden -g '!.git/**' -g '!_reference/Implem.Pleasanter/**' `
  'submodule|サブモジュール|reference-submodule|_reference' .github scripts _documents CLAUDE.md README.md
```

差分があれば進める前に所有者と意図を確認する。`.gitmodules` が無い場合の config の失敗は想定内。
Core は以前の棚卸し時点で参照更新 workflow が無かったため、無いものを新設しない。
現在のファイルと CI を正とし、過去の棚卸しの設置数を適用条件にしない。
デュアルライセンスの規約、frontend、DB、KVS、E2E、公開方式の差は維持する。

## 2. gitlink と自動更新を外す

`git ls-files --stage` で mode `160000` を確認した場合だけ、gitlink を索引から外す。
既存の参照ソースとその未コミット変更を削除しない。

```powershell
git rm --cached -- _reference/Implem.Pleasanter
git rm -- .github/workflows/reference-submodule-update.yml
git rm -- scripts/reference-submodule-check.sh scripts/reference-submodule-open-pr.sh
```

無いファイルのコマンドは省く。`.gitmodules` は該当エントリだけを削除し、
ほかのサブモジュールが無い場合に限り `git rm -- .gitmodules` する。
`.gitignore` に `_reference/Implem.Pleasanter/` を追加する。
`_reference/README.md` は追跡したままにする。
`.git/modules` の掃除や `git submodule deinit` は不要で、この手順では行わない。

## 3. スクリプトと規約を反映する

承認済み Template コミットのクリーンな作業ツリーから、新規スクリプトだけをコピーする。
以下は `$templateCommit` と `$template` を実際の値へ置き換えてから実行する。
Template の履歴・作業ツリー自体は変更しない。

```powershell
$template = 'D:\repos\VehicleVision.PleasanterTools.Template'
$templateCommit = '<承認済みTemplateの完全なコミットSHA>'
if ((git -C $template rev-parse HEAD) -ne $templateCommit) { throw 'Template の版が異なります。' }
if (git -C $template status --porcelain) { throw 'Template の作業ツリーが汚れています。' }
Copy-Item (Join-Path $template 'scripts\sync-reference.sh') scripts
Copy-Item (Join-Path $template 'scripts\test-sync-reference.sh') scripts
```

次は内容を比較して必要な節だけを移植し、アプリ固有の内容を一括上書きしない。

| 箇所 | 反映内容 |
| --- | --- |
| `scripts/reference-isolation-check.sh` | 残す。既定先と共有先をソース・ビルドから隔離する検査を移植する |
| `scripts/package.ps1` / pack 設定 | 既存の配布形式を維持し、参照ソース・Git メタデータを含めない |
| `scripts/New-FromTemplate.ps1`（存在時） | サブモジュール前提を外し、作成後に sync-reference を案内する |
| `.github/copilot-instructions.md` | 参照専用・非追跡、読む前の同期、SHA・リンク・参照日の記録を規定する |
| `CLAUDE.md` / `AGENTS.md` | 編集元の規約を参照し、sync-agents で生成する |
| `.github/audited-repos.json`（存在時） | 削除した commonFiles と対象外理由を除き、sync-reference を追加する |
| `Test-RepoAudit.ps1` / `RepoAudit.psm1`（存在時） | 参照更新検査があれば除く。設定・App の監査は他用途のため残す |
| `Test-RepoAuditLogic.ps1`（存在時） | 新しい共通ファイルと対象外指定の整合性を検証する |
| `ci.yml` など | 旧 reference-submodule-check 呼び出しがあれば除き、`submodules: false` は維持する |

CodeQL・license-check・`Directory.Build.props` などの `_reference` 除外は残す。
隔離検査に除外設定が引っかかる場合も、除外を消すのではなく、検査対象と参照取り込みを区別する。
CI に本体取得を追加しない。ネットワーク不要の `test-sync-reference.sh` だけを CI の規約検査へ追加できる。

文書は `_reference/README.md`、`README.md`、アーキテクチャ方針、開発ガイド、開発運用、
リリース手順、再利用 workflow の棚卸し・設計（存在するもの）の該当節を置き換える。
過去の棚卸しは日時付きの記録として区別し、サブモジュール更新を現行の方針として案内しない。
「バージョン固定の根拠」は **確認した完全な SHA・固定リンク・参照日** に置き換える。
過去の事実の根拠を更新する場合は、取得したソースで再確認する。実機未検証なら明記する。

## 4. 検証して通常 PR を作る

### Manual・Overview の追加作業

この節は対象リポジトリへの配布時に行う。Template の実例追加だけでは実施済みとしない。

1. 対象の `.gitmodules` と `git ls-files --stage -- resources` を読み直す。
   [Manual 用実例](references.manual.json) は 10 件、[Overview 用実例](references.overview.json) は 12 件。
   実例は 2026-10-26 の定義に基づくため、配布時の path・URL・branch の差を確認する
2. 該当する実例を対象リポジトリの直下へ `references.json` としてコピーする。
   Manual のツールは `master`、Overview のツールは `develop`。
   Manual の Implem.Pleasanter・UiThemesPreflight・ResearchDocuments・Qiita.Article は `main`。
   private の URL は既存の `.gitmodules` のものだけを使い、記事本文を記載しない
3. 参照用の mode `160000` だけを `git rm --cached -- <path>` で索引から外す。
   各 path を `.gitignore` に追加し、対応する `.gitmodules` エントリを削除する。
   本物の依存や商用 SDK などを巻き込まない。取得済みのファイル・未コミット変更は削除しない
4. 読む前に `bash scripts/sync-reference.sh` で各 branch を更新する規約へ置き換える。
   共有先の指定は `PLEASANTER_REFERENCE_DIR` でなく `--root <dir>` にする。
   README の resources 説明、旧 submodule 初期化手順、エージェント指示も対象ごとに更新する
5. `resources/` をビルド・配布・検索から隔離する既存設定を維持する。
   Overview の `scripts/export-narration.ts` は参照取得とは独立のため変更不要。
   Manual の文書生成が使う資料と参照専用ソースを区別し、CI に private の取得を追加しない

`pmc-ko/Qiita.Article` の取得には実行者本人の GitHub 認証が必要。
`gh auth login` または Git の資格情報を使い、bot の App・GitHub 設定は変更しない。
private が取得できなければ `Status=unavailable` の警告で後続へ進む。内容は未確認と明記する。
不正入力・ローカル変更などの失敗は private でも終了コード 1 になる。
一覧は 1 件でも環境変数による単一取得先の指定を無視する。
`--manifest` の明示指定先が無い場合や JSON が壊れている場合は、既定へ戻さず失敗する。

```powershell
# コピー後は対象側の references.json をレビューする。ここでは配布しない
Copy-Item (Join-Path $template '_documents\references.manual.json') references.json
# Overview では references.overview.json を使う
bash scripts/sync-reference.sh --root 'D:\references\Manual'
```

一覧で一部の項目が失敗しても、最終出力に項目数分の path・短い SHA・日付・状態が出ることを確認する。
成功と private の取得不能だけなら終了コード 0、通常の失敗を含めば非 0。
ネットワーク不要のテストでも複数件・指定 branch・private の失敗後の継続・汚れ・不正 path を確認する。

### 共通の検証と PR

実在するテスト・ビルド・配布コマンドを各リポジトリの開発ガイドと CI で確認し、追加で実行する。
Core / DotNetClient は ZIP ではなく NuGet、frontend や E2E があるアプリではその検証も省かない。
以下の環境変数を使う取得例は一覧なしのアプリ用。
Manual・Overview では代わりに `bash scripts/sync-reference.sh --root <一時取得先>` を 2 回実行する。

```powershell
bash scripts/sync-agents.sh
bash scripts/sync-agents.sh --check
bash -n scripts/sync-reference.sh
bash scripts/test-sync-reference.sh
$env:PLEASANTER_REFERENCE_DIR = Join-Path (Get-Location) 'temp\reference-check'
bash scripts/sync-reference.sh
bash scripts/sync-reference.sh
bash scripts/reference-isolation-check.sh
Remove-Item Env:PLEASANTER_REFERENCE_DIR
pwsh scripts/Test-RepoAuditLogic.ps1
npm run lint:md
dotnet build -c Release
dotnet test --no-build -c Release
git diff --check
git diff --stat
git diff --cached --summary
git ls-files --stage -- _reference
```

存在しない監査テストなどは省略理由を PR に残す。取得のネットワークが使えなければ失敗を明記し、
ローカル bare リポジトリの回帰テスト結果を記す。未実施を成功扱いにしない。
`_reference` の追跡結果に README 以外の本体ソースや gitlink が無いことを確認する。
Markdown は行長 120 を目安に折り返す（固定 URL は分割しない）。
一時取得先だけを対象を確認して片付け、共有先は消さない。

```powershell
git add --all
git diff --cached --check
git commit -m '参照ソースを必要時に取得する方式へ切り替える' `
  -m 'AI の参照専用で CI は使わないため、自動追従を廃止する。検証結果は実測値を書く。'
git push -u origin HEAD
gh pr create --repo $repo --base develop --title '参照ソースをオンデマンド取得へ切り替える' `
  --body-file <本文ファイル>
```

コードと文書など意図でコミットを分け、実際の検証結果と必要な共同著作者を本文へ記す。
PR 本文は **対象リポジトリの PR テンプレート** を読み、見出し・コメント・チェック項目を維持する。
`Closes #<対象リポジトリのIssue番号>` と正確な検証コマンド・結果、Template の採用 SHA を書く。
他リポジトリとして Template の Issue を参照する場合は
`vehiclevisionjp/VehicleVision.PleasanterTools.Template#61` と書く。
レビュー可能な通常 PR として作成し、Draft 化・マージ・force push は行わない。
