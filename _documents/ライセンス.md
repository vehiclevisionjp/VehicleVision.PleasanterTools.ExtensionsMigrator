# ライセンス

## 既定

**AGPL-3.0-or-later と商用ライセンスのデュアルライセンス**。法務の確認は完了している。
この雛形から作る新しいリポジトリは、デュアルを既定として始まる。商用ライセンスの相手は法人に限らない。

雛形が既に済ませている内容:

- `LICENSING.md`（デュアル提供の説明）と `LICENSE-COMMERCIAL.md`（商用の概要と連絡先）、`CLA.md`、署名用の Issue フォーム、
  `.github/cla/signed.yml`、`CONTRIBUTING.md` の「CLA へ署名する」の節を置いてある。これが**正本**で、使い方は次の節にある。
  製品名は `scripts/New-FromTemplate.ps1` が置換する
- `NOTICE` の冒頭 3 行（製品名・著作権表示・SPDX 行 `AGPL-3.0-or-later OR LicenseRef-PMC-Commercial`）も正本。
  4 行目以降（参考にした資料、依存の一覧）はリポジトリごとに書く。`LICENSE` は AGPL の本文で、置換では触らない
- `Directory.Build.props` は `PackageLicenseExpression` を持たない。NuGet は `LicenseRef-*` を含む式を受け付けないため。
  NuGet パッケージを公開するときは `PackageLicenseFile` で `LICENSING.md` を指し、パッケージへ含める
- `package.json` の `license` は `AGPL-3.0-or-later` のまま（`private` で公開しない。npm の式は `LicenseRef-*` を使えない）
- `.github/copilot-instructions.md` の規約 6 と 8 に、デュアル提供であることと、取り込むと商用側を提供できなくなる理由を書いてある
- 配布 ZIP に `LICENSING.md` と `LICENSE-COMMERCIAL.md` を含める（`scripts/package.ps1`）。Release 本文にもデュアルを記す

## 正本の使い方

| ファイル | 正本の範囲 | ツールごとに変える部分 |
| --- | --- | --- |
| `LICENSING.md` | 全体 | 節マーカーの内側（下の一覧） |
| `LICENSE-COMMERCIAL.md` | 全体 | 節マーカーの内側（下の一覧） |
| `CLA.md` | 全体。条文（1.1〜2.2）は 13 リポジトリで同一で、変えない | なし（製品名は置換） |
| `.github/ISSUE_TEMPLATE/cla.yml` | 全体 | なし |
| `.github/cla/signed.yml` | 先頭の注記と `signatories:` の形式 | `signatories` の中身（署名者の記録） |
| `CONTRIBUTING.md` | 見出し「CLA へ署名する」から次の `##` 見出しの手前まで | それ以外の節 |
| `NOTICE` | 冒頭 3 行 | 4 行目以降 |
| `.github/workflows/cla-check.yml` | 全体 | 節マーカー `cla-intro`（案内コメントの 1 文。下の一覧） |

正本には、Template だけの運用文（草案のバナー、「internal の Template 自身は対象外」の注記、「要確認（法務）」のブロック）を入れない。
そうした注記は、この文書や [開発運用](開発運用.md) に書く。

### 節マーカー

ツールごとに変わる部分は、HTML コメントの節マーカーで囲む。`.github/copilot-instructions.md` の `AGENT-RULES` マーカーと同じ考え方で、
マーカーの外側は全リポジトリで同一、内側は部品集から選ぶ。

```markdown
<!-- license:begin 節名=ID -->
…本文…
<!-- license:end 節名 -->
```

| ファイル | 節名 | 選ぶもの | ID |
| --- | --- | --- | --- |
| `LICENSING.md` | `release` | リリース状態の注記 | `none` / `unreleased` / `released` |
| | `usage` | A 節末尾の利用形態の段落 | `console` / `web-service` / `library` |
| | `independence` | Pleasanter との関係の導入文 | `app` / `library`（`usage` が `console`・`web-service` なら `app`、`library` なら `library`） |
| | `connection` | Pleasanter との接続方式 | `api-only` / `api` / `db-read` / `db-same` / `db-convert` / `config-write` / `none`（`api` 以降は `,` で組み合わせ可） |
| | `reference` | `_reference/` の扱い | `on` / `off` |
| | `pleasanter-note`・`deps-note` | そのリポジトリだけの補足 | `free`（自由記述） |
| | `sni` | SNI.runtime の例外の節 | `on` / `off` / `library`（ライブラリ向け。配置物を持たず、利用するアプリの配置物に入る場合） |
| | `core` | 共通部品 Core の例外の節 | `on` / `off` / `library`（Core 自身が、アプリに組み込まれた場合の扱いを述べる） |
| `.github/workflows/cla-check.yml` | `cla-intro` | 案内コメントの、提供構成を述べる 1 文 | `dual`（既定）/ `triple`（マーカーは JS のコメント `// license:begin …`） |
| `LICENSE-COMMERCIAL.md` | `sni-scope`・`sni-terms` | SNI.runtime（対象範囲の項目と、頒布先に守っていただく条件） | `on` / `off` / `library`（`sni` と同じ値） |
| | `core-terms` | 共通部品 Core との関係 | `on` / `off` / `library`（`core` と同じ値） |
| | `reference-scope` | 対象範囲の `_reference/` の項目 | `on` / `off`（`reference` と同じ値） |

- 部品の本文は [ライセンス部品](ライセンス部品.md) にある。マーカーごと貼る。外す部品も、空のマーカーを残す（位置を示すため）
- 同じ印の節（`sni` と `sni-scope`・`sni-terms`、`core` と `core-terms`、`reference` と `reference-scope`）は、必ず同じ ID にする。
  節ごとに任意だが、SNI.runtime の例外だけを `LICENSING.md` に書いて `LICENSE-COMMERCIAL.md` に書かない、といった食い違いを作らない
- 箇条書きの中のマーカーは 2 文字インデントする（リストを分断しない）
- 部品の `〈…〉` は手で埋める。埋めたあとに `〈` `〉` を残さない
- マーカーの内側を直接書き換えない。実態に合う部品が無いときは、部品集と正本を同じ PR で直す

### 監査（RepoAudit）

`scripts/Test-RepoAudit.ps1` が、各リポジトリの `develop` の上記ファイルを正本と比べる（`.github/audited-repos.json` の `licenseFiles`。結果は「ライセンス」の列）。

- マーカーの外側、`CLA.md`・`cla.yml`・`CONTRIBUTING.md` の CLA 節・`NOTICE` の冒頭 3 行・`signed.yml` の先頭の注記（署名の記録と、その後ろの `#` の注記は自由）を、製品名の置換だけ許して比べる
- マーカーの内側は、ID が部品集（トリプルは別の定義）にあること、`free` 以外の本文が部品集と一致すること（`〈…〉` は手で埋めた本文を許し、`〈` `〉` が残れば差）を確かめる
- 同じ印の節（`sni`・`core`・`reference`。`core` は `on` / `library` を `core-terms` と同じ ID にする）と `usage`・`independence`、`cla-intro` と提供構成の食い違いも差にする
- 提供構成は `audited-repos.json` の `licenseTier`（既定 `dual`、DotNetClient は `triple`）
- 正本や部品集を直したら、`Test-RepoAuditLogic.ps1` が Template 自身との一致を確かめる

### 事実の断定文は、実態で確認してから使う

`LICENSING.md` の「Pleasanter との関係」は、**本体のコードを複製・改変・リンク・プロジェクト参照していない、派生著作物ではない、
本体の AGPL の汚染を受けておらず受け入れない**と断定する（マーカーの外側。全リポジトリで同じ）。
この断定は、各リポジトリの実態が合っていて初めて成り立つ。適用や新規作成のたびに、次を確認する。

- csproj・`Directory.Packages.props` に Pleasanter のアセンブリやプロジェクトへの参照が無い（`scripts/reference-isolation-check.sh` が通る）
- 本体のコードをコピー・流用していない（参考にした一次情報は `_documents/アーキテクチャ方針.md` などに残す）
- 選んだ `connection` が、実際の通信方式（API・DB の接続・設定ファイル）と合っている
- `reference` が実態と合っている（`_reference/` を持つか）
- `usage` が実際の提供形態と合っている
- SNI.runtime が配置物に入るか（csproj と配置物、`packages.lock.json` があればそれで確認）を見て `sni` を決める
- Core.Data / Core.Mail / Core.Web に依存するか（csproj で確認）を見て `core` を決める（アプリは `on`。Core 自身は `library`）

確認できない事実は、断定せず、`pleasanter-note` に確認していない旨を書く（DotNetClient の LGPL の層のように、別に扱う）。

### 新しいリポジトリを作るとき

1. `scripts/New-FromTemplate.ps1` で名前を置換する。正本の製品名は `VehicleVision.PleasanterTools.Template` の文字列で、置換が済ませる
2. 上の確認をしたうえで、`LICENSING.md`・`LICENSE-COMMERCIAL.md` の節マーカーを実態に合わせて選び直す。
   雛形の既定は `release=none`・`usage=console`・`connection=api-only`・`reference=on`・`sni=off`・`core=off`
3. `NOTICE` の 4 行目以降と `README.md` を実態に合わせる。`.github/cla/signed.yml` は `signatories: []` のまま始める

### 既存のリポジトリへ適用するとき

1. 該当リポジトリの `LICENSING.md`・`LICENSE-COMMERCIAL.md` を、Template の正本で置き換える（製品名を置換する）
2. 節マーカーの内側を、そのリポジトリの実態に合う部品へ置き換える。元の文言にあった固有の事実は、部品か `*-note` へ移す
3. `CLA.md`・`.github/ISSUE_TEMPLATE/cla.yml` は正本で置き換える。`signed.yml` は注記を正本に合わせ、`signatories` の記録は残す。
   `CONTRIBUTING.md` は「CLA へ署名する」の節だけ置き換える。`NOTICE` は冒頭 3 行だけ合わせる。
   `.github/workflows/cla-check.yml` は正本で置き換える（`cla-intro` は `dual`。トリプルのリポジトリだけ `triple`）
4. 署名の効力はツールごと（`CLA.md` が「本ソフトウェア」をツールごとに定義しているため）。署名の記録を他のリポジトリへ複写しない
5. 公開済みの版が別の提供条件のときは `release=released`、未公開のときは `release=unreleased` を選ぶ

### トリプルライセンスの正本

LGPL の A 層・AGPL・商用の 3 層で提供するツール（DotNetClient）は、デュアルの正本ではなく、
別の正本 [ライセンス正本（トリプル）](ライセンス正本-トリプル.md) を使う。
層の数と記号（A=LGPL・B=AGPL・C=商用）が本文の大半に及ぶため、節マーカーの部品ではなく別の一式にした（理由は同書）。

- 構成は同書の「全文」。`LICENSING.md`・`LICENSE-COMMERCIAL.md`・`CLA.md`・`CONTRIBUTING.md` の CLA 節・`NOTICE` の冒頭 3 行を、トリプル用に置き換える。
  `cla.yml` と `signed.yml` はデュアルの正本と同じ。`cla-check.yml` もデュアルの正本を使い、案内文の節 `cla-intro` だけ `triple` を選ぶ
- 節マーカーの規則は上と同じ。選べる ID は同書の「節マーカー（トリプル）」にある。
  `usage`・`connection`・`reference`・ノートの部品は、[ライセンス部品](ライセンス部品.md) と同じ本文を使う
- A 層の範囲（利用の目的で決める。公的機関は含めない）は法務確認済みで、正本の本文から変えない
- 適用するときの手順と確認は、同書の「適用するとき」。デュアルの「事実の断定文」の確認項目は、トリプルでも同じ
- デュアルの正本を直したときは、同書の「デュアルとの差分」で「同じ」の行を見直す（Pleasanter の節・依存の節・CLA の導入文など）

## 新しいリポジトリを作る人が守る条件

デュアルライセンスを成り立たせる前提なので、雛形から作ったあとも守る。公開する前に確認する。
Questionnaire（`VehicleVision.PleasanterTools.Questionnaire`）が実例。

1. **権利を確認する。** 自社の著作権または必要な再許諾の権利が全コードにあること。
   外部からの貢献は [CLA](../CLA.md) で再許諾を受ける。
   手順は [開発運用](開発運用.md) の「公開リポジトリの CLA」に従う
2. **Pleasanter 本体を取り込んでいないこと。** 本体の著作権は自社に無く、取り込むと商用側を提供できない。`scripts/reference-isolation-check.sh` が通ること。
   Pleasanter との関わり方が標準 API だけでなくなる場合は、`connection` の部品を実態に合わせる
3. **依存が寛容ライセンスだけであること。** MIT / BSD 系 / Apache-2.0。フォントのみ SIL OFL 1.1 も可。
   GPL・AGPL・LGPL の依存が無いことを `NOTICE` と csproj（`packages.lock.json` があればそれも）で確認する
   （当社の共通部品 Core だけは、`core` の節に書いたうえで使える）

`Microsoft.Data.SqlClient.SNI.runtime`（Microsoft Software License Terms）は寛容ライセンスの一覧にない。
SQL Server 用の SqlClient を使い SNI.runtime が配置物に入るときは、`sni` を `on` にする
（`LICENSING.md` の例外の節と `LICENSE-COMMERCIAL.md` の「頒布先に守っていただく条件」が入る）。
`NOTICE` と配布物の記載も合わせる。雛形には SNI.runtime への依存が無いので、既定は `off`。
ライブラリ（Core）のように、SqlClient への依存を宣言するだけで配置物を持たず、利用するアプリの配置物に SNI.runtime が入る場合は、
`library` にする（事実の記述と、アプリ側の頒布条件への案内だけで、新しい条件は足さない）。

提供条件を AGPL 単独へ変える場合や、LGPL の層を設ける場合は、雛形の既定から外れる。
個別に法務と判断する（LGPL の層を設ける場合の正本は [ライセンス正本（トリプル）](ライセンス正本-トリプル.md)）。どの提供条件でも、**1 の権利確認と CLA は必須**。2・3 と規約 8（寛容ライセンスの依存のみ）も常に守る。
internal の Template 自身は CLA の対象外で、この一式は新規公開リポジトリへ配る正本として置いている。
